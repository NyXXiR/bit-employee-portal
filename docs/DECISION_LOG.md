# 설계 결정 대장

결정이 바뀌더라도 기존 내용을 지우지 않고 새 항목으로 변경 이유를 기록한다.

## D-001 퇴사 후 기존 세션 차단

- 상태: 확정
- 선택: 퇴사 처리 커밋 후 기존 세션의 다음 보호 요청부터 접근을 거부한다.
- 이유: 로그인 상태가 남아 권한 철회 의도와 어긋나는 동작을 방지하기 위해서다.
- 구현 영향: 현재 재직 상태 또는 세션 버전을 서버에서 확인하고, 민감한 쓰기는 DB 갱신
  시점에도 재직 조건을 검사한다.
- 반대 선택의 장점: 토큰 만료까지 허용하면 구현과 DB 조회가 단순하다.
- 틀릴 수 있는 상황: 미래 퇴사 시각이나 인수인계 유예 시간을 지원해야 하는 정책이 있다면
  즉시 차단 대신 효력 발생 시각이 필요하다.

## D-002 이름 입력과 외부 API 매핑

- 상태: 확정
- 선택: 성과 이름을 별도 필드로 입력하고 관리자가 예외를 수정한다.
- 이유: 한글 전체 이름을 코드로 자동 분해하면 복성 및 짧은 이름에서 잘못 추정할 수 있다.
- 구현 영향: `lastName=성`, `firstName=이름`의 단순한 외부 API 계약을 유지한다.
- 반대 선택의 장점: 전체 이름 하나만 받으면 입력 UI와 기존 데이터 가져오기가 단순하다.
- 틀릴 수 있는 상황: 다양한 국가의 이름 체계를 본격 지원한다면 성/이름 강제 모델 자체가
  적절하지 않을 수 있다.

## D-003 생년월일 누락 처리

- 상태: 확정
- 선택: 누락을 허용하되 직원에게 즉시 보완을 유도하고 관리자가 발견하고 대신 수정할 수
  있게 한다. 값이 보완되기 전에는 Background Check만 차단한다.
- 이유: 한 필드의 누락으로 전체 사이트가 실패해서는 안 되며, 업무 중 데이터 품질을
  회복할 경로가 필요하다.
- 구현 영향: nullable 모델, 프로필 경고, 관리자 표시, 변경 권한 및 감사 기록이 필요하다.
- 반대 선택의 장점: 관리자만 수정하게 하면 검증되지 않은 자기신고 정보의 유입을 줄인다.
- 틀릴 수 있는 상황: 생년월일이 법적으로 검증된 인사 원장 데이터여야 한다면 직원 직접
  변경 대신 승인 절차가 필요하다.

## D-004 Background Check 중복 방지

- 상태: 방향 확정, 세부 구현은 기술 스택 선택 후 확정
- 선택: UI, 도메인 계약, DB 제약의 세 단계에서 중복을 방지한다.
- 이유: UI 방어와 애플리케이션의 선행 조회만으로 동시 요청 경쟁 상태를 막을 수 없다.
- 구현 영향: idempotency key 유일성, 직원별 활성 검사 유일성, 명시적인 상태 전이가 필요하다.
- 반대 선택의 장점: 외부 API 호출 후 결과만 저장하는 단순 구조는 구현 시간이 짧다.
- 틀릴 수 있는 상황: 외부 API가 강한 멱등성 키와 중복 제거를 공식 지원한다면 로컬 계약을
  일부 단순화할 수 있다.

## D-005 단일 Next.js 애플리케이션

- 상태: 확정
- 선택: 별도 Next/Nest 모노레포 대신 단일 Next.js 앱 안에서 UI, Route Handler, 서버 전용
  도메인 및 DAL 계층을 분리한다.
- 이유: 하나의 인증 경계와 배포 단위로 요구사항을 충족할 수 있으며 6시간 안에 핵심 권한과
  외부 API 안정성에 더 많은 시간을 사용할 수 있다.
- 반대 선택의 장점: 독립 백엔드는 팀과 배포 주기, 확장, 기술 선택을 분리하기 쉽다.
- 틀릴 수 있는 상황: 프론트엔드와 백엔드를 다른 팀이 운영하거나 관리자 API가 별도 네트워크
  경계를 가져야 한다면 독립 서비스가 더 적합하다.

## D-006 외부 API의 Retry-After 우선

- 상태: 확정
- 선택: 결과 조회 중 외부 API가 503과 `Retry-After`를 반환하면 내부 응답의 헤더와 본문에
  같은 대기 시간을 전달한다. 값이 없을 때만 실측으로 정한 기본 간격을 사용한다.
- 이유: 장애 중인 외부 서비스가 제시한 회복 시간을 무시한 고정 폴링은 부하를 키우고 복구를
  방해할 수 있다.
- 반대 선택의 장점: 고정 간격만 사용하면 프론트 상태와 테스트가 단순하다.
- 틀릴 수 있는 상황: 외부 서비스의 `Retry-After`가 신뢰할 수 없거나 과도한 값이라면 상한과
  하한을 별도로 적용해야 한다.

## D-007 세션 거부 사유 구분

- 상태: 확정
- 선택: 유효한 세션이 없다는 결과를 만료, 명시적 폐기, 퇴사로 구분하되 모두 인증 실패로
  처리한다.
- 이유: 접근 통제를 약화하지 않으면서 사용자가 재로그인해야 하는지 인사 담당자에게 문의해야
  하는지 정확하게 안내할 수 있다.
- 반대 선택의 장점: 모든 실패를 같은 401로 처리하면 인증 코드와 노출 정보가 최소화된다.
- 틀릴 수 있는 상황: 세션 상태 자체가 공격자에게 유용한 정보가 되는 공개 서비스라면 상세
  사유는 서버 로그에만 남기는 편이 안전하다.

## D-008 Background Check 실행·열람 권한 통합

- 상태: 확정
- 선택: 현재의 단일 `ADMIN` 역할에는 검사 실행과 결과 열람 권한을 함께 부여하며, 별도의
  열람 동작과 `BACKGROUND_CHECK_VIEWED` 감사 이벤트는 만들지 않는다.
- 이유: 모든 관리자가 두 권한을 함께 갖는 과제 범위에서는 별도 열람 API와 감사 기록의 운영상
  편익이 작고, 단순 페이지 진입을 열람으로 기록하면 로그의 의미도 불명확해진다.
- 반대 선택의 장점: 명시적 열람은 우발적 노출을 줄이고 누가 결과를 봤는지 추적할 수 있다.
- 틀릴 수 있는 상황: 관리자 역할이 인사 운영자·검사 담당자 등으로 나뉘거나 컴플라이언스상
  열람 추적이 필요해지면 권한을 분리하고 명시적 열람 API를 추가해야 한다.

## D-009 신규 사번은 DB에서 자동 발급

- 상태: 확정
- 선택: 시드 사번 `EMP-001`~`EMP-010`은 유지하고 신규 직원은 PostgreSQL sequence로
  `EMP-011`부터 발급한다. 사번은 생성 후 변경하지 않는다.
- 이유: 핵심 업무 식별자를 수기로 받으면 오입력이 외부 검사와 감사 이력까지 전파된다. DB
  sequence는 동시 생성에서도 중복 없이 하나의 발급 규칙을 강제한다.
- 반대 선택의 장점: 관리자가 입력하면 기존 HR 시스템이 발급한 사번을 그대로 사용할 수 있다.
- 틀릴 수 있는 상황: 회사의 HR 원장이 사번의 권위 있는 발급 주체라면 로컬 sequence 대신
  HR 연동으로 받은 값을 검증해 저장해야 한다.

## D-010 fullName은 저장하지 않고 파생

- 상태: 확정
- 선택: `fullName`은 성과 이름을 합쳐 응답에서 만들며 DB에 중복 저장하지 않는다. 검색은
  성·이름 각 컬럼과 두 컬럼의 경계를 지나는 모든 분할을 조회한다.
- 이유: 현재 규모에서는 정확한 부분 검색을 쿼리 조합으로 해결할 수 있고, 저장 컬럼의 동기화
  규칙과 마이그레이션을 추가할 편익이 작다.
- 반대 선택의 장점: 생성 컬럼과 trigram 인덱스를 사용하면 대량 데이터의 부분 검색이 단순하고
  빠르다.
- 틀릴 수 있는 상황: 직원 수나 검색 부하가 커져 다수의 OR 조건과 `%contains%` 조회가 병목이
  되면 PostgreSQL 생성 컬럼과 `pg_trgm` GIN 인덱스를 도입해야 한다.

## D-011 직원 레코드와 로그인 계정의 생명주기 분리

- 상태: 확정
- 선택: 직원 레코드는 로그인 계정 없이 존재할 수 있다. 관리자는 재직 중이며 계정이 없는
  직원에게 로그인 아이디와 초기 비밀번호를 한 번 발급할 수 있고, 이 동작을 별도 도메인
  명령과 감사 이벤트로 기록한다.
- 이유: 기존 직원 데이터 이관이나 향후 SSO 연동에서는 인사 레코드 생성 시점과 접근 권한
  부여 시점이 다를 수 있다. 프로필 수정에 자격증명 변경을 섞으면 권한과 감사 의미도
  불명확해진다.
- 구현 영향: 목록과 상세 응답에 nullable `loginId`를 제공하고, 계정이 없는 재직 직원에게만
  `POST /api/admin/employees/:employeeId/account`를 허용한다. 기존 계정의 아이디 변경과
  비밀번호 재설정은 별도 정책이 확정되기 전까지 허용하지 않는다.
- 반대 선택의 장점: 모든 직원 생성 시 계정을 강제하면 미발급 상태가 없어지고 운영 절차가
  단순하다.
- 틀릴 수 있는 상황: 권위 있는 사내 IdP가 계정 생명주기를 전담하게 되면 로컬 비밀번호
  발급 대신 초대 또는 SSO 연결 상태를 관리해야 한다.
