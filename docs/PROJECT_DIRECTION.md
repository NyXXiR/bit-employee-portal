# 핵심 방향성

## 1. 문서의 목적

이 문서는 과제 설명서와 Swagger를 그대로 옮긴 명세가 아니다. 요구사항 분석 과정에서
확정한 구현 원칙과 아직 검증하거나 선택해야 하는 사항을 구분해 기록한다. 구현 중 충돌이
생기면 이 문서를 우선 확인하고, 방향을 바꿀 때는 `DECISION_LOG.md`에 근거를 남긴다.

## 2. 과제의 우선순위

이 과제의 핵심은 많은 기능을 만드는 것이 아니라 다음을 입증하는 것이다.

1. 인증과 권한 경계가 서버에서 강제된다.
2. 퇴사 처리 후 접근 권한이 의도대로 즉시 사라진다.
3. 불완전한 직원 데이터가 있어도 시스템 전체는 정상 동작한다.
4. 외부 Background Check API의 불확실성과 중복 요청을 통제한다.
5. 타임아웃, 재시도, 폴링 값은 실제 측정 결과에서 도출한다.
6. 선택과 한계를 면접에서 코드 수준으로 설명할 수 있다.

## 3. 확정된 핵심 방향

### 3.1 퇴사 처리는 접근 권한의 즉시 철회다

- 퇴사 직원 레코드를 삭제하지 않고 재직 상태와 퇴사 시각을 기록한다.
- 퇴사 처리 완료 후 시작되는 모든 보호 요청은 거부한다.
- 로그인 토큰에 들어 있는 과거 상태만 신뢰하지 않고, 보호 요청마다 현재 계정 상태 또는
  세션 폐기 여부를 서버에서 확인한다.
- 퇴사 처리 트랜잭션에서 직원 상태 변경과 세션 무효화 정보를 함께 갱신한다.
- 화면에서 메뉴를 숨기거나 로그아웃시키는 것은 보조 수단일 뿐 권한 통제가 아니다.
- 퇴사 처리와 동시에 진행 중이던 요청까지 완전히 되돌리는 것은 별개의 동시성 문제다.
  최소 계약은 "퇴사 트랜잭션 커밋 후 시작된 요청은 거부"로 정의한다. 직원의 자기 정보
  수정처럼 민감한 쓰기는 DB 갱신 시점에도 `ACTIVE` 조건을 다시 확인한다.

검증 시나리오:

1. 직원이 로그인한다.
2. 관리자가 해당 직원을 퇴사 처리한다.
3. 직원이 기존 세션으로 조회 및 수정을 다시 시도한다.
4. 두 요청 모두 거부되고 데이터가 변경되지 않는지 확인한다.

### 3.2 이름은 성과 이름을 명시적으로 입력한다

- 직원 이름 입력 UI는 `성`과 `이름`을 별도 필드로 강제한다.
- 화면 표시 이름은 두 필드를 조합한다.
- 외부 API에는 `lastName=성`, `firstName=이름`으로 전달한다.
- 문자열 길이만으로 한 글자 성과 복성을 자동 추정하는 범용 로직은 만들지 않는다.
- 남궁, 황보, 선우 등 복성이나 기타 예외는 관리자가 입력 또는 수정한다.
- 시드 데이터는 원문의 전체 이름이 바뀌지 않도록 명시적 매핑을 사용한다.

초기 시드 매핑:

| 사번 | 성 | 이름 | 표시 이름 |
|---|---|---|---|
| EMP-001 | 김 | 민준 | 김민준 |
| EMP-002 | 김 | 민준 | 김민준 |
| EMP-003 | 남궁 | 서준 | 남궁서준 |
| EMP-004 | 황보 | 라온 | 황보라온 |
| EMP-005 | 김 | 솔 | 김솔 |
| EMP-006 | 선우 | 진 | 선우진 |
| EMP-007 | 이 | 서연 | 이서연 |
| EMP-008 | 박 | 민준 | 박민준 |
| EMP-009 | 최 | 지우 | 최지우 |
| EMP-010 | 정 | 하윤 | 정하윤 |

`선우진` 등의 분리가 실제 인사 정보와 다를 수 있다는 점은 데이터 한계로 명시하며,
관리자가 수정할 수 있어야 한다.

### 3.3 생년월일 누락은 장애가 아니라 보완 가능한 데이터 상태다

- 생년월일은 DB에서 nullable로 저장한다.
- 생년월일이 없어도 로그인, 자기 정보 조회, 관리자 직원 목록은 정상 동작해야 한다.
- 로그인한 직원에게 프로필 상단 경고와 명확한 보완 동작을 제공한다.
- 관리자는 목록 배지, 필터 또는 요약 카운트로 미완성 프로필을 발견할 수 있어야 한다.
- 직원 본인과 관리자 모두 생년월일을 보완할 수 있도록 하되, 누가 언제 어떤 값으로
  변경했는지 기록한다.
- 생년월일이 없거나 형식이 유효하지 않으면 Background Check 요청은 서버에서 거부한다.
- 누락값을 임의의 날짜로 대체하거나 외부 API 오류에 맡기지 않는다.
- 이미 완료된 검사의 요청 정보는 이후 프로필 수정과 섞이지 않도록 요청 당시의 이름과
  생년월일 스냅샷을 유지한다.
- 프로필 변경은 과거 검사 스냅샷을 수정하거나 자동 재검사를 만들지 않는다. 서버는 요청 당시
  정보와 현재 프로필의 일치 여부 및 달라진 필드만 계산해 관리자에게 제공한다.

권한 원칙:

| 동작 | 직원 본인 | 관리자 |
|---|---:|---:|
| 생년월일 누락 여부 조회 | 가능 | 가능 |
| 본인 생년월일 보완 | 가능 | 가능 |
| 다른 직원 생년월일 보완 | 불가 | 가능 |
| 변경 이력 전체 조회 | 기본 불가 | 가능 |
| Background Check 실행 | 불가 | 가능 |

### 3.4 Background Check는 UI가 아니라 서버와 DB가 중복을 막는다

버튼 비활성화만으로는 새로고침, 다중 탭, 네트워크 재전송, 동시 요청을 막을 수 없다.
중복 방지는 다음 세 층에서 수행한다.

1. UI: 진행 중 표시와 중복 클릭 방지
2. 도메인 계약: 동일 명령의 재실행과 동일 직원의 동시 검사를 구분
3. DB 제약: 경쟁 상태에서도 활성 검사 레코드가 둘 이상 만들어지지 않게 보장

권장 명령 계약:

- 요청마다 클라이언트가 생성한 `idempotencyKey`를 전달한다.
- 같은 `idempotencyKey`의 반복 요청은 새 외부 호출을 만들지 않고 기존 로컬 요청을 반환한다.
- 다른 키라도 같은 직원에게 `REQUESTING` 또는 `PENDING` 검사가 있으면
  `ACTIVE_CHECK_EXISTS` 충돌로 처리한다.
- `CLEAR`, `FLAGGED`, 최종 실패 상태 이후에는 관리자가 새 키로 재검사를 요청할 수 있다.
- DB에는 `idempotencyKey` 유일 제약과 직원별 활성 검사 유일 제약을 둔다.
- 직원 생성, 퇴사, 생년월일 변경과 같은 다른 도메인 명령도 중복 실행에 안전하도록
  상태 전이 조건과 유일 제약을 함께 사용한다.

상태 모델 초안:

```text
REQUESTING -> PENDING -> CLEAR
                    \-> FLAGGED
REQUESTING -> FAILED
PENDING    -> FAILED
```

`REQUESTING`은 로컬 요청은 접수했지만 외부 `checkId` 저장이 끝나지 않은 상태다.

외부 API에는 idempotency key 계약이 명시되어 있지 않다. 따라서 외부 POST 성공 직후
애플리케이션이 중단되고 `checkId`를 저장하지 못하는 구간에서는 exactly-once를 완전히
보장할 수 없다. 이때 자동으로 외부 POST를 다시 보내면 중복 검사가 생길 수 있으므로,
기본 정책은 해당 요청을 불확실 상태로 남기고 관리자 재확인 대상으로 표시하는 것이다.
실제 API의 동일 `employeeId` 반복 POST 동작을 측정한 후 이 정책을 재검토한다.

## 4. API 측정과 구현의 관계

다음 값은 관행으로 정하지 않고 실측 후 확정한다.

- 요청 타임아웃
- 최대 재시도 횟수
- 재시도 간격
- 최초 및 후속 폴링 간격
- 재시도 중단 조건
- 동시 요청 제한

측정 원본에는 요청 시각, 응답 시간, 상태코드, 응답 헤더, `checkId`, 상태 변화,
`estimatedCompletionSeconds`, `createdAt`, `completedAt`, 동시성 수준을 남긴다.

## 5. 권한 및 민감정보 원칙

- 직원은 자기 정보만 조회하고 허용된 필드만 수정한다.
- 관리자는 직원 관리와 Background Check 기능을 사용한다.
- 권한은 모든 서버 엔드포인트에서 다시 검사한다.
- Background Check 상세 결과는 관리자에게만 노출한다.
- 현재 단일 관리자 역할에는 검사 실행과 결과 열람 권한을 함께 둔다. 역할이 세분화되면
  결과 조회 권한을 별도 권한으로 분리한다.
- 비밀번호, 세션 토큰, API 비밀값, 전체 민감 응답을 애플리케이션 로그에 남기지 않는다.
- 개인정보 변경과 Background Check 실행에는 행위자와 시각을 기록한다.
- 퇴사 상태, 역할, 사번은 직원 본인이 수정할 수 없다.

## 6. 확정된 기술 구조

- Node.js 20.9.0
- Next.js 16.3.4, React 19, TypeScript, App Router
- Prisma 6.12와 PostgreSQL 전용 `bit_employee_portal` 데이터베이스의 `public` 스키마
- 단일 Next.js 실행 프로세스와 Nginx reverse proxy
- Route Handler를 HTTP 경계로, `src/server`를 서버 전용 DAL 및 도메인 계층으로 사용
- DB 기반 opaque session과 HttpOnly cookie
- 직원 UI는 `/portal`, 관리자 UI는 `/admin`으로 구분

별도 프론트엔드·백엔드 앱은 만들지 않는다. 6시간 과제에서 두 실행 단위는 인증, 배포,
CORS, 공통 타입 관리 비용을 늘리지만 요구사항 충족에 직접 기여하지 않기 때문이다.

## 7. 구현 우선순위

1. 기술 스택과 배포 방식 확정
2. DB 모델, 상태 전이, 제약 조건 확정
3. 외부 API 탐색 및 측정 스크립트 실행
4. 조기 배포와 DB 연결 확인
5. 로그인, 서버 권한 검사, 퇴사 세션 차단
6. 직원 및 관리자 핵심 기능
7. Background Check와 중복 방지
8. 권한·동시성·장애 시나리오 검증
9. 배포 검증과 제출 문서 정리

## 8. 아직 확정해야 하는 사항

- 직원의 이름 직접 수정 허용 여부
- 관리자 생년월일 수정 시 추가 확인 또는 사유 입력 여부
- 개인정보 변경 이력의 구체적인 저장 범위
- Background Check 결과 보존 기간
- `REQUESTING` 불확실 상태의 운영 처리 방식
- 측정 결과에 따른 타임아웃, 재시도, 폴링 값
- 직원 생성 시 초기 비밀번호 전달 방식

## 9. 범위 통제

6시간 내 핵심 안전성을 우선한다. 이메일 초대, 비밀번호 찾기, 복잡한 승인 흐름,
실시간 알림, 조직도, 정교한 디자인은 기본 제외 대상으로 둔다. 제외 기능과 이유는
README 및 최종 제출 문서에 명시한다.
