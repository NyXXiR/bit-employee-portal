## 한 줄로

Background Check API는 **GET 요청의 63%가 실패하도록 장애가 주입돼 있고**, 명세와 실제가
여러 군데 어긋난다. 그 안에서 동작하는 타임아웃·재시도·폴링 값을 실측으로 정하고,
정한 값을 다시 100회 돌려 예측이 맞는지까지 확인했다.

## 무엇을 쟀나

2026-09-03 15:20~17:18 UTC, 약 2시간. 관측 **1,964건**.

| 항목 | 표본 수 | 어떻게 |
|---|---|---|
| GET 지연 / 상태코드 | 1,000 | 단일 순차 요청. 50건씩 20배치, 배치 간 90초 |
| pending→최종 | 40 | POST 40건 후 2초 주기 폴링 |
| 같은 employeeId POST 반복 | 6 | 연속 POST |
| 동시성 | 레벨당 100 | 레벨 1 / 5 / 10 / 20 |
| 명세 대조 프로브 | 각 1 | 없는 ID 조회, 잘못된 입력, DELETE 등 |
| **정책 검증** | 100 | 정한 정책 그대로 실행 |

**표본 수를 이렇게 잡은 이유**가 중요하다. p99를 최댓값과 분리하려면 최소 100건,
안정적으로 추정하려면 `10/(1-0.99)` = 1,000건이 필요하다. 비율을 ±3%p로 말하려면
역시 1,000건 근처가 필요하다. 그래서 GET만 1,000건을 채웠고, 외부에 쓰기가 나가는
POST 계열은 비용이 커서 40건에서 멈췄다.

배치 사이를 90초씩 벌린 건 **연속으로 때리면 웜 컨테이너 하나의 분포만 재게 되기 때문**이다.

## 알아낸 것 5가지

### 1. 성공 응답에 1.2초짜리 공백이 있다 ← 타임아웃의 근거

성공한 373건을 정렬하면 이렇게 생겼다.

```
… 561, 563, 572, 577, 590  │  1810,  5120, 5306, 5401, 6217, …
        빠른 무리 끝 590ms ─┤  공백 1.2초
```

| 타임아웃 | 전체 요청 대비 성공률 |
|---|---|
| 1초 | 25.3% |
| 5초 | 25.4%  ← **+0.1%p** |
| 30초 | 37.3% |

1초를 5초로 늘려서 얻는 게 0.1%p다. 그 사이에 성공 응답이 사실상 없다.
1초 너머의 성공을 잡으려면 30초까지 기다려야 하는데, 그 30초짜리 응답의 대부분은
성공이 아니라 게이트웨이가 끊는 503이다.

### 2. 오류가 서로 독립이다 ← 백오프를 안 쓰는 근거

n=1,000에서 앞뒤 요청을 이어 붙여 봤다.

```
P(실패 | 직전도 실패) = 62.6%
P(실패 | 직전은 성공) = 62.7%
전체 실패율           = 62.7%
```

세 값이 같다. **장애가 몰려 오지 않는다**는 뜻이고, 따라서 **기다린다고 성공 확률이
오르지 않는다.** 지수 백오프는 "장애가 지속된다"는 전제 위에 서는 기법인데
이 API는 그 전제를 만족하지 않는다. 그래서 500ms 고정 간격을 쓴다.
그 500ms도 회복을 기다리는 시간이 아니라 서버를 두드리는 속도를 제한하는 값이다.

### 3. 30초 벽이 있다

지연 29초 이상 응답이 1,000건 중 96건(9.6%). 그중 93건이 503이다.
API Gateway 통합 타임아웃으로 보인다. 명세에는 없다.

이것 때문에 **전체 분위수를 정책 근거로 쓸 수 없다.** p95·p99·max가 전부 30,000ms에
붙는데, 이건 지연 분포가 아니라 게이트웨이가 끊는 지점을 재고 있는 것이다.
그래서 성공 응답만 따로 뽑아 봤고, 거기서 1번의 공백이 나왔다.

### 4. 장애가 GET에만 주입돼 있다

| | 표본 | 결과 |
|---|---|---|
| GET | 1,000 | 200 37.3% / 500 37.5% / 503 25.2% |
| **POST** | **46** | **201 100%.** p50 46.6ms, max 97.7ms |

POST는 한 번도 실패하지 않았다. 그래서 타임아웃과 재시도를 GET/POST로 나눴다.

### 5. `retryAfter`가 헤더가 아니라 본문에만 있다 ← 함정으로 보인다

명세는 503 응답에 `Retry-After` **헤더**를 정의하면서
"Clients should honour this value instead of using a fixed backoff"라고 못박았다.
그리고 본문 스키마에도 `retryAfter` 필드를 뒀다.

실제로는:

```
Retry-After 헤더  :   0 / 509 건
본문 retryAfter   : 303 / 509 건  (값은 전부 상수 30)
```

명세대로 헤더만 읽는 구현은 `null`을 받고, **아무 경고 없이 고정 백오프로 떨어진다**
— 명세가 하지 말라고 한 바로 그 동작으로. 조용히 실패해서 테스트로도 안 잡힌다.
우리 코드는 헤더 → 본문 순으로 둘 다 읽어서 통과한다.

한 겹 더 있다. `retryAfter`는 **빨리 돌아온 503에만** 붙는다.

| 503 종류 | 건수 | p50 지연 | retryAfter |
|---|---|---|---|
| 본문에 retryAfter 있음 | 303 | 32.8ms | "30초 기다려라" |
| `{"message":"Service Unavailable"}` | 206 | 30,013ms | 없음 |

**33ms만에 답해 놓고 30초를 기다리라 하고, 정작 30초를 잡아먹었을 때는 아무 말이 없다.**
값을 곧이곧대로 따르면 가장 빨리 회복된 경우에 가장 오래 기다리게 된다.

## 정한 값 4개

### 타임아웃 — GET 1초 / POST 3초

GET 1초는 위 1번(1.2초 공백)에서 나왔다. 590ms에 여유 1.7배.
POST 3초는 관측 max 97.7ms의 30배. 짧게 잡을 이유가 없다 —
**서버가 중복을 제거하지 않으므로** 성급히 끊으면 검사가 중복 생성될 위험만 커진다.

기대 소요로 비교하면 짧은 타임아웃 + 재시도가 **5배 빠르다.**
1초면 기대 2.7초, 30초면 기대 14.5초(실패 한 번에 30초씩 태우니까).

### 재시도 — GET 4회 · 500ms 고정 / POST 없음

4회는 1회 성공확률 25.3%에서 나왔다. 누적 68.9%, 최악 벽시계 5.5초.
10회로 늘려도 94.6%에 그치고 15초가 걸린다. 그 구간은 자동 재시도 대신
실패를 화면에 노출하고 관리자가 다시 누르게 하는 편이 낫다(2회 클릭이면 90.3%).

간격을 늘리지 않는 이유는 위 2번(독립성).

POST에 재시도를 안 하는 이유가 두 가지다. 실패를 한 건도 관측하지 못했고
(rule of three로 상한 6.5%), 더 중요하게는 **같은 employeeId로 POST 6회에
checkId가 6개 생겼다.** 응답을 못 받은 POST를 재시도하면 검사가 중복 생성된다.
중복 방지는 클라이언트 `idempotencyKey`로 한다.

### 폴링 주기 — 첫 4초, 이후 5초, 180초에 종료

**POST 응답의 62.5%가 이미 최종 상태였다.** 이 경우 폴링을 아예 시작하지 않는다.

pending을 거친 15건의 완료 시각(초):

```
4.6  6.2  8.3  9.2  12.1  12.3  14.7  15.3  16.0  30.1  38.8  39.9  43.5  47.1  53.8
```

최단이 4.6초라 첫 조회는 4초 뒤. 그 전에 물어봐야 pending만 돌아온다.
이후 5초 간격이면 완료 발견 지연 상한이 5초다.

180초 종료는 **이 표본이 아니라 다른 실측(n=409)에서 가져왔다.**
n=40으로는 꼬리를 신뢰할 수 없어서, 120초 내 93.64% / 180초 내 97.80%를
관측한 쪽(표본 10배)을 택했다. 측정 조건이 다르다는 건 문서에 적어 뒀다.

### 재시도 중단 조건

1. **400 또는 404** — 반복해도 회복 안 됨
2. **4회 소진** 또는 **5.5초 경과** — 먼저 오는 쪽
3. **응답 스키마 위반**
4. **생성 후 180초** — 자동 조회 종료, `UNKNOWN`으로 두고 수동 재조회 대상
5. **`retryAfter`는 중단·대기 조건으로 안 씀** — 위 5번

여기서 제일 중요한 건 **500을 "대상 없음"으로 해석하지 않는 것**이다.
실측에서 없는 checkId 조회가 어떤 실행에서는 500, 다른 실행에서는 명세대로 404를
반환했다. **주입된 500이 진짜 404를 가린다.** 확정 신호로 쓸 수 있는 건 404뿐이다.

## 정한 값을 다시 검증했다

예측만 적어두면 근거가 약하니, 정책 그대로 100회 돌렸다.
(정책 상수를 베껴 쓰지 않고 `src/lib/polling.ts`에서 직접 import해서 실행)

| | 예측 | 실측 | 95% CI |
|---|---|---|---|
| 1회 시도 성공률 | 25.3% | **25.0%** | [20.2, 30.5] |
| 4회 누적 성공률 | 68.9% | **68.0%** | [58.3, 76.3] |

둘 다 신뢰구간 안에 들어왔다. 이 값들이 "오류가 독립"이라는 가정 위에서 계산된 거라,
**그 가정 자체가 검증된 셈**이다.

### 벽시계는 예측이 틀렸다 (내 계산 오류)

예측 2,680ms인데 실측 1,252.8ms로 2배 빨랐다.
무제한 기하분포의 기댓값(3.95회)을 4회에서 끊는 정책에 그대로 갖다 썼는데,
실제로는 늦게 성공했을 회차가 실패로 빠져나가므로 성공은 앞쪽에 몰린다
— **성공한 68회의 평균 시도는 2.12회**였다.

조건부 기댓값을 무조건부로 쓴 것이고, API가 아니라 내가 틀렸다.
방향이 안전한 쪽(정책이 문서보다 빠름)이라 값은 그대로 뒀다.

→ **제출물 4의 B 항목("AI가 처음에 잘못 만든 지점, 어떻게 발견했는지")에 그대로 쓸 수 있다.**
발견 수단은 테스트도 코드 리딩도 아닌 **실측**이었다.

## 솔직히 부족한 것

인터뷰에서 물어보면 이렇게 답하면 된다.

**1. 지연 표본 1,000건이 전부 순수한 단일 순차 요청은 아니다.**
800건에서 중단하려고 프로세스에 종료를 보냈는데 죽지 않고 20배치를 끝까지 채웠고,
그 사이 동시성 단계를 이어붙여서 **마지막 4배치(200건)가 겹친다.**
겹치지 않는 800건만으로 다시 계산한 표를 문서 1절 끝에 넣어 뒀다 — 결론은 동일하다
(p50 43.5 vs 42.6ms, 1.2초 공백 양쪽 모두 존재, 1→5초 증가폭 둘 다 0.1%p).

**2. 동시성 레벨 1 표본 187건은 오염돼서 버렸다.**
같은 겹침의 반대 방향이다. 대신 지연 단계 n=1,000을 동시성 1의 기준선으로 썼다.
조건이 같고 표본이 10배라 더 나은 대체다.

**3. pending n=40은 몸통만 믿을 수 있다.** 꼬리는 다른 실측(n=409)에 의존했고
그쪽은 동시성 5 조건이라 측정 조건이 다르다.

**4. `GET /background-checks?employeeId=`는 200을 한 번도 못 봤다.**
다만 오류율 62.7%에서 3회 프로브면 우연히 다 실패할 확률이 24.6%다.
그래서 **"고장났다"가 아니라 "미확인"으로 남겼다.** 이 엔드포인트에 의존하는 기능은 안 만들었다.

**5. `retryBudgetMs`(5.5초)는 100회 검증에서 한 번도 발동하지 않았다.**
최대 벽시계가 4,598ms였다. 최악의 경우를 막는 안전장치인데 실전 검증은 안 된 상수다.

**6. flagged 비율은 측정 못 했다.** 이번 40건이 전부 clear였다.

**7. 정책 검증 100회는 응답 본문을 기록하지 않았다.**
상태코드만 남겼다. 나중에 "그 503들이 어느 종류였나" 같은 질문에는 답할 수 없다.

## 코드 어디에 들어가 있나

숫자를 문서에만 적어두지 않고 전부 코드에 반영했다. 인터뷰에서 파일 열어 보여주면 된다.

| 결론 | 위치 |
|---|---|
| 타임아웃 GET 1초 / POST 3초 | `src/server/env.ts` |

각 상수 옆 주석에 어느 수치에서 나왔는지 적혀 있다.
